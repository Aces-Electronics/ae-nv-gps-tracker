# Design Decisions

## 2026-10-30 Derive the BLE Pairing Passkey from the BLE Address
- **Context**: PR #17 made the tracker's BLE require a pairing PIN, derived from the Wi-Fi base MAC (`esp_read_mac(ESP_MAC_WIFI_STA)`). The phone app derives the PIN it shows differently: from the BLE address it sees, last octet minus two (`MacUtils.getWifiMacFromBleMac`, then `generatePinFromMac`). The two agree only when the Bluetooth MAC is the base MAC plus two, which is what the old comment in `ble_handler.cpp` asserted. It is an SDK build setting (`CONFIG_ESP32S3_UNIVERSAL_MAC_ADDRESSES`): 4 on ESP32 and ESP32-C3, but 2 on the ESP32-S3 with the Arduino 2.0.17 core, where Bluetooth is base plus one. The last release (0.0.59, 2026-09-04) was built on platform 7.1.0 with `framework-arduinoespressif32 3.20017.241212`, which is that core, and every memory variant's `sdkconfig.h` (including `qio_opi`, which this tracker uses) has the value 2. So on a released tracker the passkey was the PIN of the base MAC and the app showed the PIN of (base - 1): a phone following the app's PIN was refused. The same defect was found and confirmed on hardware on the Smart Hut PDU (an ESP32-S3 on the same core; its BLE address read `...03:ED` for Wi-Fi MAC `...03:EC`).
- **Options Considered**:
  1. *Keep the base MAC and change the app to subtract one for S3 devices*: the app only has the BLE address and the advertised name, not the chip or SDK, so it cannot know the offset.
  2. *Read the base MAC and add the SDK's offset as a constant*: correct today, silently wrong the moment the platform changes.
  3. *Derive from the BLE address minus two, as the app does (Chosen)*.
- **Chosen Decision**: `generatePinFromMac()` reads `esp_read_mac(ESP_MAC_BT)` and passes it to `blePinFromBtMac()` in the new `src/ble_pin.h`, which subtracts two from the last octet (wrapping inside the octet, never borrowing) and takes the last three octets modulo 1,000,000. The arithmetic is pure and host-tested (`pio test -e native`, `test/test_ble_pin`); expected values are what real boards printed.
- **Rationale**: Both ends derive the PIN from the same address, so they agree on any SDK build and any chip, with no offset to keep in step. Existing bonds are unaffected (the PIN is only used to pair); a phone that has not bonded must use the PIN the app shows, which is now the right one. On a build where Bluetooth is already base plus two this changes nothing. Trackers still running 0.0.59 keep the old passkey until updated.
- **Not verified**: no tracker was on the bench. The conclusion rests on the SDK configuration and the PDU hardware result, not on reading a tracker's BLE address. The release env builds locally on platform 6.9.0 (same framework package); the PR's CI is the check on the pinned platform.

## 2026-10-30 Pin the PlatformIO Platform to 7.1.0
- **Context**: `platform = espressif32` was unpinned, and every other env extends this one. The sibling Smart Hut PDU firmware had the same line; its CI for a one-file change installed the then-newest platform, 8.0.0 (Arduino-ESP32 3.3.12), and failed to compile, because the CI cache is keyed on the hash of `platformio.ini` and the previous cache had expired. This project's last successful release run (2026-09-04, firmware 0.0.59) used platform 7.1.0 with `framework-arduinoespressif32 3.20017.241212` (Arduino core 2.0.17).
- **Options Considered**: (1) Leave it unpinned and hope 8.0.0 builds: untested, and the PDU shows it can silently not. (2) Port to Arduino-ESP32 3.x: right eventually, but a re-validation of the modem, sleep and BLE paths, not a fix. (3) Pin to 7.1.0, the platform of the last release (Chosen).
- **Chosen Decision**: `platform = espressif32@7.1.0` in the base env; all other envs inherit it. The native test env is unaffected.
- **Rationale**: A release should be built by the toolchain it was validated on. The Bluetooth MAC offset behind the pairing PIN is an SDK build setting, so a floating toolchain would also float the passkey; the derivation now reads the BLE address and does not depend on it, but the pin keeps everything else stable too.
- **Not verified**: this laptop builds with 6.9.0 (same framework package), so 7.1.0 itself is checked only by the PR's CI. Whether the tracker would have built on 8.0.0 was not tested.
